# Catalogs

Tenant-scoped allow-lists for the AppForge generator. These files are the **single source of truth** for what `Control:` types, `Variant:` values, and properties may appear in generated PA-YAML.

If something isn't in the catalogs, the generator must refuse with an `error: missing-catalog-entry` block (see `../README.md` → "Error contract") rather than guessing.

**The augmentations layer is the moat, not the cost.** A year of hand-curated knowledge is not redundant overhead on top of the auto-extractor — it is captured tenant-runtime truth that the MCP can't produce on its own. `Gallery.OnSelect` (verified) and a handful of others are real input properties the schema accepts but `describe_control` doesn't surface. The diff at `cli/diff-report.md` is the evidence; `control-augmentations.yml` is where it lives.

## Family labels

`FluentV9` in `control-manifest.yml` is the earlier modern generation with bare type names (`Text`, `TextInput`, `Button`, `TabList`, `Icon`, etc.). `React` is the current `Modern*` family. Generate current types directly; Studio Update is lossy. See the compile and Studio evidence, 2026-10-06. Generated manifest and property files are not changed by this correction.

## Files

| File | Purpose | Source |
|---|---|---|
| `control-manifest.yml` | Allow-list of valid `Control:` types. Names, families, variants. | Auto-generated, do not hand-edit |
| `control-properties.yml` | Per-control property allow-lists, enum definitions, parent-conditional bundles. | Auto-generated, do not hand-edit |
| `control-augmentations.yml` | Hand-curated overlay: notes, MCP-omitted properties, legacy variants. | **Hand-edit only** |

The validator reads all three. `control-augmentations.yml` overlays the auto-generated files: any `additional_input_properties` are unioned into the control's `input_properties`; `notes` are surfaced in error messages; `current_variants` records current presets the extractor omits, each with a name, `verified: true`, ISO `verified_at` and `verified_by: compile_canvas`; their names are surfaced in the merged current variant list. Both these presets and `legacy_variants` are accepted as `Variant:` values using the common property surface when no extracted variant bundle exists. Keep the vocabularies disjoint and retire a current augmentation when extraction includes its name. See `cli/diff-report.md` for the diff that justifies each augmentation entry.

## Provenance

Both files are auto-generated by `../../cli/extractor.mjs`. The manifest's `source:` block records the cluster category and MCP source; environment and app IDs are not published. **Do not hand-edit either file** — re-run the extractor instead.

```
node cli/extractor.mjs catalogs
```

Requires `CANVAS_ENVIRONMENT_ID`, `CANVAS_APP_ID`, `CANVAS_CLUSTER_CATEGORY` env vars set to a tenant where you have an open coauthoring session.

Evidence labels such as `field-report-YYYY-MM-DD#n`, `studio-export-*` and `scratch-compile-*` name the maintainers' evidence records; field reports are not published, and the evidence class travels with each entry.

## Architectural caveat: versioning is not enforceable

The original AppForge design assumed `Control: <Type>@<Version>` notation, with the catalog refusing on `(Type, Variant, Version)` mismatches. **This premise no longer holds:**

- `describe_control` does not expose per-control version numbers.
- `sync_canvas` emits PA-YAML without `@x.y.z` suffixes.

The refusal contract is therefore weaker than originally specified. We can refuse on `(Type, Variant, Family)` mismatches, but **we cannot detect "control X used to support property Y but a new release dropped it."** Mitigation:

1. Every catalog file carries `extracted_at:` and the published manifest carries the cluster category and MCP source in `source:`.
2. Schedule re-extraction on a regular cadence (suggest: per Power Apps monthly release, or whenever a generated app fails to compile against the catalog).
3. The validator should warn when the catalog is older than N days.

This is a real reduction in precision vs. the original design, not a cosmetic one. If/when versioning resurfaces in the MCP or the YAML schema, the extractor should be updated to populate the `version:` field that's reserved on every manifest entry today.

## Schema reference

See header comments in each `.yml` file for the schema. Key conventions:

- **Enum types** are deduped to a top-level `enums:` map; properties reference them via `"@enum:<Name>"` strings (loader-agnostic, no YAML tags required).
- **Inline enums** (where MCP returns `Enum (a, b, c)` without an explicit name) are synthesized using the property name. The extractor warns on collisions where the same synthesized name would have divergent values.
- **Parent-conditional layout properties** live in `parent_context_properties:` bundles (`vertical_horizontal_autolayout_child`, `grid_layout_child`); each control declares which bundles apply via `parent_context:`.
- **Event handlers** (`OnSelect`, `OnVisible`, `OnChange`, etc.) are tagged `Event` rather than `Boolean` — the MCP types them as `Boolean` but they're formula slots, not predicates. Heuristic: any property whose name starts with `On` and whose MCP type is `Boolean`.
- **Multi-variant controls** (`GroupContainer`, `Gallery`) declare `variants:` and a `variant_input_properties:` map keyed by variant name. The Variant: value selects which extra property bundle merges into `input_properties:` for validation.
- **Two MCP-named enums with identical value-sets are NOT collapsed** even if they're semantically the same. Example: `Layout` and `LayoutDirection` both have values `[Horizontal, Vertical]` and stay as separate entries — the MCP gave them different names, so the catalog respects that.

## Known limitations

- Gallery's `Vertical` and `Horizontal` variants both have empty `variant_input_properties` because the MCP doesn't surface per-variant property differences. From the catalog's perspective, Gallery's `Variant:` is a name allow-list with no property gate; whether the variants behave differently at runtime is a runtime concern, not a generation concern.
- 9 controls (listed above) currently un-extractable due to upstream service errors.
