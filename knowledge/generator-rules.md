# Power Apps Canvas YAML — Generator Rules

You are generating **Canvas App YAML** that is pasteable into Power Apps Studio (controls + Power Fx).  
Do **not** generate OpenAPI or custom-connector specs.

## 0) Output Contract
- Output **valid YAML only**. No prose, comments, or Markdown formatting.
- Indentation: **2 spaces** per level. No tabs. No trailing commas.

## 0a) Output Scope (Detect from User Intent)

Detect what the user wants and emit the appropriate structure:

| User Intent | Output Structure |
|-------------|------------------|
| "a button", "give me a checkbox" | **Single control** — just the control block |
| "a header with title and buttons", "a filter row" | **Control cluster** — `Children:` list with multiple controls |
| "a screen for...", "build me a page" | **Full screen** — `Screens:` with one screen |
| "a component for..." | **Component** — see `component-rules.md` |

### Single Control
```yaml
- btnSubmit:
    Control: ModernButton
    Properties:
      Text: ="Submit"
```

### Control Cluster
```yaml
Children:
  - grpHeader:
      Control: GroupContainer
      Variant: ManualLayout
      Properties:
        Height: =60
      Children:
        - lblTitle:
            Control: Label
            Properties:
              Text: ="Page Title"
        - btnAction:
            Control: ModernButton
            Properties:
              Text: ="Action"
```

### Full Screen
```yaml
Screens:
  ScreenName:
    Properties:
      Fill: =RGBA(245, 245, 245, 1)
    Children:
      - grpMain:
          # ... container structure
```

### Component
See `component-rules.md` for component-specific structure.

**Detection hints:**
- Singular noun ("a button", "a label") → Single control
- Plural or grouped ("buttons", "a row of", "header with") → Cluster
- "screen", "page", "view" → Full screen
- "component", "reusable" → Component

### File Output Structure
When saving generated YAML, use this folder structure:

| Output Type | Folder | Example |
|-------------|--------|---------|
| Screen | `/screens/` | `/screens/ProjectListScreen.yaml` |
| Control (single) | `/controls/` | `/controls/btnSubmit.yaml` |
| Control cluster | `/controls/` | `/controls/HeaderRow.yaml` |
| Component | `/components/` | `/components/UserCard.yaml` |

**Naming conventions:**
- Screens: PascalCase with "Screen" suffix → `ProjectListScreen.yaml`
- Controls: camelCase matching control name → `btnSubmit.yaml`, `grpHeaderRow.yaml`
- Components: PascalCase → `UserCard.yaml`, `StatusBadge.yaml`

## 1) Top-Level Shape
```yaml
Screens:
  <ScreenName>:
    Properties: <PropertyMap>            # optional
    Children: <ControlList>              # optional
```

## 2) Control Block Shape
Each control is a **single-key map** inside `Children`. The key is the instance name.

```yaml
- <InstanceName>:
    Control: <Type>                      # required
    Variant: <VariantName>               # optional (only if present in catalog)
    Layout: <LayoutName>                 # optional (e.g., Form/FormViewer "Vertical")
    Group: <GroupName>                   # optional (e.g., chart/media composites)
    Properties: <PropertyMap>            # optional
    Children: <ControlList>              # optional (containers/galleries/forms)
```
**Notes**
- `Variant`, `Layout`, and `Group` are **siblings** of `Properties:` (not nested under it).
- If a container/gallery has templated children, include a nested `Children:` with its item template controls.

### Block scalars

For an unquoted inline formula, `|-` is required when it contains `: ` (colon followed by a space), even inside a Power Fx string: Power Fx quotes do not quote YAML. YAML-quoted formulas are already protected. `validate_yaml` refuses only this colon-space hazard (`block-scalar-required`).

For pasting through Studio's code view, `|-` is recommended for `;`, `{` or `}` outside Power Fx strings (`inline-formula-paste-hygiene`, WARN). These inline formulas compile and sync as-is, and Studio writes them this way. Preserve the formula's original spacing and line breaks.

## 3) Catalog (Single Source of Truth)

The catalog is a **three-file triple** under `catalogs/`:

| File | Source | Purpose |
|---|---|---|
| `control-manifest.yml` | Auto-generated by `cli/extractor.mjs` from the canvas-authoring MCP | Allow-list of valid `Control:` types, families, variants |
| `control-properties.yml` | Auto-generated | Per-control `input_properties`, `variant_input_properties`, `output_properties`, `parent_context_properties`, `enums` |
| `control-augmentations.yml` | **Hand-curated** — never auto-overwritten | Notes, MCP-omitted properties (with `verified` flag), legacy variants |

**Why three files:** The MCP's `describe_control` is broad but not complete. It misses real properties (e.g., `Gallery.OnSelect`) and contains stale relics. Auto-extraction gets us most of the way; hand-augmentation captures the rest. The augmentations layer is **the moat, not the cost** — it's a year of accumulated tenant-runtime truth that the MCP cannot produce.

### Type rendering

Render `Control:` as the **bare type** (no `@version` suffix) as this repository's generation convention. This is not a universal claim about the active `.pa.yaml` schema or every authoring surface. In existing source, pins are observations: a suffix alone establishes neither lag nor incompatibility. Consult the selected authoring surface and the version-lag inventory for exact evidence-backed migrations; unknown mappings remain unresolved. Do not automatically remove pins:

```yaml
Control: ModernButton
Control: Classic/DropDown
Control: GroupContainer
Variant: AutoLayout
```

If a control type is missing from `control-manifest.yml`, return:

```yaml
error: missing-catalog-entry
detail: control-type-not-in-manifest
controlType: "<Type>"
```

Never guess. The catalog is authoritative.

## 3a) Modern vs Classic Defaults (MANDATORY)

Choose controls in this order:

1. **Default: the current `Modern*` control** — `ModernText`, `ModernTextInput`, `ModernButton`, `ModernCheckbox`, `ModernCombobox`, `ModernDatePicker`, `ModernDropdown`, `ModernRadio`, `ModernToggle`, `ModernSlider`, `ModernTabList`, `ModernIcon`, `ModernNumberInput`, `ModernLink`, etc. The catalog labels this family `React`. Owner decision and generation evidence, 2026-10-06; this changes generation defaults, not catalog verification flags.
2. **Do not generate the bare FluentV9 types** (`Text`, `TextInput`, `Button`, `CheckBox`, `ComboBox`, `DropDown`, `DatePicker`, `Radio`, `Toggle`, `Slider`, `TabList`, `Icon`). They are the previous modern generation; see the compile and Studio evidence, 2026-10-06. Never rely on Studio's “update control versions”: it converts these types to `Modern*` and silently drops styling, including `Size` and `VerticalAlign`.
3. **Icons: use `ModernIcon`, including `OnSelect`.** It compiled and its action ran in Preview on 2026-10-06. Use `Classic/Icon` only for a required classic `Icon` enum value with no `ModernIcon` text name. Icon names differ; review the name rather than deleting an action.
4. **Classic only for a missing capability the catalog proves.** Name the required missing property in the spec or a comment. Re-checked against `Modern*`, 2026-10-06: `Classic/ComboBox` for required `DisplayFields`/`SearchFields`; `Label` for `Tooltip`, `TabIndex`, `Role` or `Live` (but not `OnSelect`, which `ModernText` has); `Classic/TextInput` for `Format: =TextFormat.Number` (no numeric `ModernTextInput.Type`). `Classic/Button` remains an option for exact `Fill`/`HoverFill`/`PressedFill` overrides absent on `ModernButton`. The map records draft manual conversions and behaviour losses; no pair is verified.
5. **Galleries: current layouts are Gallery presets.** Use `Gallery` with `ModernText` and other current controls inside it, and put row taps on `Gallery.OnSelect`. The three compile-verified `BrowseLayout_*_ver5.0` presets in `current_variants` are current Studio layouts omitted by the extractor. Inside a gallery in a component definition, do not use `Select(Parent)`, even on a direct gallery child; put the action on the gallery's `OnSelect` or the control's own `OnSelect`. Direct children of screen-level galleries may still use `Select(Parent)` (runtime comparison, 2026-10-06, items 7–8). Use `ModernTabList` or `Table` when either does the whole job.
6. **Practice (owner, 2026-10-06):** prefer `ModernCombobox` over `ModernDropdown`; use checkboxes for choices where several may apply.
7. **Modern radio uses `OnChange`.** On `ModernRadio`, use `OnChange`, not `OnSelect`; the current catalog confirms the event. The 2026-05-10 compile stamp is historical radio evidence, not a verification of this map.
8. **The existing app is not a template (owner, 2026-11-12).** When you add to an app, build the new parts from these
   rules, not by copying what neighbouring screens do. Superseded control types, workarounds and formula patterns
   already in the app stay where they are, and new controls do not inherit them. The authoring service's notice "do not
   use X unless it's already present in this app" does not apply here: an existing `Button` is no reason for a new
   one. Match the app's look by reusing its values (colours, fonts, sizes, named formulas), with current controls.
   Copy existing controls or patterns only when the user asks for that, for example "make it look exactly like the
   other screen" or "keep the old buttons", and say so in the plan. Field report, 2026-11-12: a new dashboard screen
   got bare `Button` and `Text` controls because the app already used them. With the earlier copy of the app
   (`before_files`, or a sibling `before` folder at the compile gate), AppForge warns about each new control that uses
   a superseded type (`new-control-superseded-type`).

## 4) Properties, Events, Variants — Tiered Allow-List

The catalog operates in **three tiers**, evaluated by `cli/validate.mjs` (which the generator pipeline calls before emitting YAML).

### Merge logic

For each control type, the effective allow-list is the **union** of:

1. `control-properties.yml`:
   - `controls.<Type>.input_properties` (always available)
   - `controls.<Type>.variant_input_properties.<ChosenVariant>` (only when emitting that variant)
   - `parent_context_properties.<bundle>` for every bundle in `controls.<Type>.parent_context` (only when the parent matches the bundle's preconditions, e.g. AutoLayout-child props on a child of an AutoLayout `GroupContainer`)
2. `control-augmentations.yml`:
   - `controls.<Type>.additional_input_properties` — entries here are added to the allow-list, **with verification status carried through**

### Three-state validation

For each property the generator wants to emit, the validator returns one of:

| State | When | Generator behaviour |
|---|---|---|
| **PASS** | Property is in `control-properties.yml`, OR in `control-augmentations.yml` with `verified: true` | Emit. No diagnostic. |
| **WARN** | Property is in `control-augmentations.yml` with `verified: false` (the default for new entries) | Emit. Log a warning naming the unverified property. Tracking: usage frequency drives the verification queue — verify the augmentations that actually fire in real generations first. |
| **REFUSE** | Property is in neither | Stop. Return the `missing-catalog-entry` error block (below). Never invent a property. |

### Variants

A `Variant:` value is accepted when it appears in either:
- `control-manifest.yml` → `controls.<Type>.variants` (auto-extracted), or
- `control-augmentations.yml` → `controls.<Type>.current_variants` (compile-verified current presets omitted by the extractor, including the three `BrowseLayout_*_ver5.0` Gallery layouts), plus `legacy_variants` for old layouts such as the two Gallery `ver4.0` entries

Otherwise, refuse with `variant-not-in-catalog`.

### Refusal contract

```yaml
error: missing-catalog-entry
detail: property-or-variant-not-in-catalog
controlType: "<Type>"
key: "<PropertyOrVariantName>"
```

### Verification workflow for new augmentations

When a hand-author adds an entry to `control-augmentations.yml.additional_input_properties`, default it to `verified: false` (shorthand: `PropName: Type`). To promote to verified: write a minimal PA-YAML that uses the property, run `compile_canvas` against a live tenant. If accepted, replace the shorthand with longhand and set `verified: true, verified_at: <date>, verified_by: compile_canvas`. **If rejected, REMOVE the entry** — false claims pollute the WARN tier and erode trust in the warning signal.

## 5) Power Fx Rules
- **Leading equals:** every formula value starts with `=`.
- **No pretty-printing:** do **not** insert or remove newlines/spaces inside formulas. Preserve exactly what's provided.
- **Named colors require prefix:** Color names must be prefixed with `Color.` (e.g., `Color.Transparent`, `Color.Red`, `Color.Blue`). Never use bare color names like `Transparent`.
- **Block scalars for safety, without reformatting.** Use `|-` for unquoted inline formulas containing `: `; recommend it for `;`, `{` or `}` outside strings when pasting, or for formulas longer than **120** characters. `validate_yaml` refuses only the colon-space hazard and warns for paste punctuation. Keep a single-line source formula as a **single line** immediately under the key. Example:

```yaml
OnSelect: |-
  =Collect(colObservations, {ObsId: "O" & Text(CountRows(colObservations) + 1, "000"), PersonUPN: varObsPerson, Month: Text(Today(), "yyyymm"), Title: varObsTitle, Point1: varObsPoint1, Point2: varObsPoint2, Point3: varObsPoint3, Point4: varObsPoint4, Point5: varObsPoint5, Checked1: false, Checked2: false, Checked3: false, Checked4: false, Checked5: false, Acknowledged: false, AcknowledgedOn: Blank(), ManagerUPN: User().Email}); Set(varNewObs, false)
```
- **Colon-space in text anywhere:** if a string contains `: `, put the whole formula into a block scalar (keep as one line):

```yaml
Text: |-
  ="Owner: " & ThisItem.Owner
```
- Colors use Power Fx (`RGBA(...)`, `ColorValue("#RRGGBB")`) unless replaced by theme tokens per exemplar.
- **Theme consistency for dropdowns, comboboxes and date pickers:** use consistent theme colors through properties supported by the selected control. The following sample describes classic theming; modern controls use their cataloged theming surface:
  ```yaml
  BorderColor: =RGBA(207, 221, 224, 1)
  ChevronBackground: =RGBA(249, 251, 251, 1)
  ChevronFill: =RGBA(59, 108, 125, 1)
  ChevronHoverBackground: =RGBA(220, 230, 232, 1)
  ChevronHoverFill: =RGBA(47, 94, 111, 1)
  HoverFill: =RGBA(249, 251, 251, 1)
  SelectionFill: =RGBA(59, 108, 125, 1)
  SelectionColor: =RGBA(255, 255, 255, 1)
  IconBackground: =RGBA(249, 251, 251, 1)  # For DatePicker
  IconFill: =RGBA(59, 108, 125, 1)  # For DatePicker
  ```
- **SharePoint lookup patching:** When patching lookup columns, use the proper record format:
  ```yaml
  # For required lookups:
  Verksamhetsomrade: {Id: varSelectedVerksamhet.ID, Value: varSelectedVerksamhet.Title}

  # For optional lookups (can be blank):
  Underenhet: If(!IsBlank(varSelectedUnderenhet), {Id: varSelectedUnderenhet.ID, Value: varSelectedUnderenhet.Title}, Blank())
  ```
  Note: SharePoint expects lowercase 'Id' in the record structure
- **Column name quoting in Power Fx functions:**
  - AddColumns: NO quotes for new column names: `AddColumns(table, NewColumn, "value")`
  - ShowColumns/DropColumns: NO quotes: `ShowColumns(table, Column1, Column2)`
  - GroupBy: NO quotes: `GroupBy(table, ColumnName, GroupName)`
  - SortByColumns: WITH quotes: `SortByColumns(table, "ColumnName")`
  - For Choice columns in GroupBy, extract value first: `GroupBy(AddColumns(data, StatusValue, Status.Value), StatusValue, Group)`
- **Division by zero protection:** When using Max() or Count in division operations, protect with If():
  ```yaml
  Width: =If(CountRows(collection) > 0, (ThisItem.Count / Max(collection, Count)) * size, 0)
  ```
- Literal tokens (e.g., `Layout: Vertical`, `Variant: Horizontal`) are allowed where exemplars show literal usage; otherwise prefer Power Fx for numeric positions (`X: =20`, etc.).

Answer "yes" internally to all:

## 12) LayoutMinWidth / LayoutMinHeight Default Trap

**Power Apps defaults are `LayoutMinWidth: =250` and `LayoutMinHeight: =100`.**

If you do NOT explicitly set these, Power Apps applies these defaults automatically, causing overflow and content being cut off in most layouts.

**You MUST explicitly set `LayoutMinWidth` and `LayoutMinHeight` on EVERY container and control inside an AutoLayout parent.**

Typical values:
- Stretched children (`AlignInContainer.Stretch`): `LayoutMinWidth: =0` — gets width from parent
- Labels: `LayoutMinHeight: =20` to `=30` depending on font size
- Icon containers: match the fixed size (e.g., `LayoutMinWidth: =35`, `LayoutMinHeight: =35`)
- Galleries with `FillPortions: =1`: `LayoutMinWidth: =0`, `LayoutMinHeight: =0`

**CRITICAL**: A large `LayoutMinWidth` on a stretched item causes overflow. When `AlignInContainer: =AlignInContainer.Stretch`, always set `LayoutMinWidth: =0`.

## 13) FillPortions vs Height/Width — Mutually Exclusive

**Never set both `FillPortions: =1` (or higher) and a static `Height`/`Width` on the same axis.** They contradict each other:

| Situation | What to do |
|---|---|
| Size to children (field group, fixed section) | `FillPortions: =0` + explicit `Height` formula |
| Fill remaining space proportionally | `FillPortions: =1` — explicit `Height` is **ignored** |
| Fill with minimum size constraint | `FillPortions: =1` + `LayoutMinHeight: =N` |
| Fill with maximum size constraint | `FillPortions: =1` + `LayoutMaxHeight: =N` |

**Rule:** Once `FillPortions > 0`, any static Height/Width on that axis is overridden by fill. Use `LayoutMinHeight`/`LayoutMaxHeight` to constrain fill behavior.
- Vertical AutoLayout → `FillPortions` controls **Height**
- Horizontal AutoLayout → `FillPortions` controls **Width**

## 14) AlignInContainer — ALWAYS Set Explicitly

Every child inside an AutoLayout container **MUST** have `AlignInContainer` set explicitly. Never rely on the parent's `LayoutAlignItems` as the default.

**Why:** If the parent has `LayoutAlignItems: Stretch` (common default), any child without its own explicit `AlignInContainer` silently stretches on the cross-axis, overriding its fixed size and breaking circles, icons, and badges.

| Parent direction | Cross-axis | What `Stretch` overrides |
|---|---|---|
| `Horizontal` | Height | Child's fixed `Height` |
| `Vertical` | Width | Child's fixed `Width` |

**Decision guide:**

| What the child should do | Set on child |
|---|---|
| Fill the full cross-axis (labels, content areas, inputs) | `AlignInContainer: =AlignInContainer.Stretch` |
| Labels needing vertical centering in a **horizontal** parent | `AlignInContainer: =AlignInContainer.Stretch` + `VerticalAlign: =VerticalAlign.Middle` |
| Keep its own fixed size, centered on cross-axis | `AlignInContainer: =AlignInContainer.Center` |
| Keep its own fixed size, pinned to start | `AlignInContainer: =AlignInContainer.Start` |
| Keep its own fixed size, pinned to end | `AlignInContainer: =AlignInContainer.End` |

> **ANTI-PATTERN**: Do NOT use `AlignInContainer: Center` on a label to achieve vertical centering. A centered label only occupies its natural height and creates gaps above/below in taller rows. Use `AlignInContainer: Stretch` + `VerticalAlign: Middle` instead.

## 15) Scroll Container Children Sizing Rule

When a `GroupContainer` has `LayoutOverflowY: =LayoutOverflow.Scroll`, its **direct children that contain the scrollable content** MUST use `FillPortions: =0` with an explicit `Height`. **NEVER** use `FillPortions: =1` on content that should be scrollable.

**Why `FillPortions: =1` defeats scrolling:** It sizes the child to exactly fill the scroll viewport height. The child cannot grow beyond the viewport — content is pinned to viewport size and overflows are clipped. The scroll viewport never activates.

**Correct scroll pattern:**
```yaml
- scrollableBody:
    Variant: AutoLayout
    Properties:
      FillPortions: =1
      LayoutOverflowY: =LayoutOverflow.Scroll
    Children:
      - contentWrapper:
          Properties:
            FillPortions: =0
            Height: =formCard.Height + 48   # explicit Height required
          Children:
            - formCard:
                # actual content (taller than viewport = scroll activates)
```

**Wrong pattern (scroll never activates):**
```yaml
Children:
  - contentWrapper:
      Properties:
        FillPortions: =1   # WRONG — pins child to viewport height
```

## 16) Overlay Button Pattern — Mandatory ManualLayout

Any `GroupContainer` that contains a transparent overlay button (`Classic/Button` with `Fill: =RGBA(0,0,0,0)`) as a child **MUST** be `Variant: ManualLayout`.

**Why:** In an AutoLayout container, an overlay button with `Height: =Parent.Height` stacks alongside siblings and consumes the entire container height, leaving sibling controls with 0px height (invisible).

**How to convert:**
1. Change `Variant: AutoLayout` to `Variant: ManualLayout`
2. Remove: `LayoutDirection`, `LayoutAlignItems`, `LayoutJustifyContent`, `LayoutGap`, `LayoutWrap`, `LayoutMinWidth`, `LayoutMinHeight`
3. Remove `AlignInContainer` from all children
4. Add explicit `X`, `Y`, `Width`, `Height` to every child
5. Place the overlay button **LAST** in `Children:` — last = rendered on top

```yaml
- itemContainer:
    Control: GroupContainer
    Variant: ManualLayout
    Properties:
      Width: =Parent.Width
      Height: =44
      Fill: =RGBA(0,0,0,0)
      DropShadow: =DropShadow.None
    Children:
      - itemLabel:
          Control: Label
          Properties:
            X: =12
            Y: =0
            Width: =Parent.Width - 24
            Height: =40
      - itemOverlay:
          Control: Classic/Button
          Properties:
            Text: =""
            Fill: =RGBA(0,0,0,0)
            HoverFill: =RGBA(0,0,0,0.08)
            PressedFill: =RGBA(0,0,0,0.16)
            BorderStyle: =BorderStyle.None
            X: =0
            Y: =0
            Width: =Parent.Width
            Height: =Parent.Height
            OnSelect: =false
```

## 17) Wrap=false on Single-Line Labels

Every `Label` that displays on **one line** MUST have `Wrap: =false` set explicitly.

Power Apps defaults `Wrap` to `true`. On a narrow container, a label without `Wrap: =false` will unexpectedly split to two lines even when text fits visually.

**Always add `Wrap: =false` to:**
- Logo text labels
- Navigation item labels (sidebar and top nav)
- Tab bar item labels
- Column headers in tables and galleries
- Status badge text
- KPI metric values and card titles
- Breadcrumb text labels
- Button-adjacent text labels

**Omit `Wrap` (leave as default `true`) only for:**
- Multi-line description fields
- Body copy paragraphs
- Error message labels where text length is variable

**Sizing rule for single-line labels in horizontal containers:**
Do NOT set a fixed `Width` that barely fits the expected text — even 1px too narrow triggers wrapping. Instead use `FillPortions: =1` or `Width: =Parent.Width` with `Wrap: =false`.
