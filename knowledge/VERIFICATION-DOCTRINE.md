# AppForge verification doctrine

How contributors should work in this codebase.

## Architectural principle: every component must have a verification gate

**Every component AppForge ships must have a verification gate that runs before the component is relied on.** Without one, the component accumulates errors that look like load-bearing truth, indistinguishable from real signal until something far downstream finally notices.

### What this looked like in practice

The hand-curated property table (now retired) was treated as a year of accumulated tenant-runtime truth. Batch verification with `compile_canvas` tested 22 of its claims against a live tenant:

- 4 verified real (all on `Gallery`: `OnSelect`, `WrapCount`, `TemplateFill`, `ItemAccessibleLabel` — confirmed MCP omissions)
- 18 rejected as manual catalog errors

Without the verification step, those 18 ghost rules would have lived in `control-augmentations.yml` permanently. They would have fired as WARN in real generations, polluting the queue that's supposed to drive verification prioritisation. The "manual catalog as captured runtime truth" framing was overgenerous — what got accumulated was 4 real findings and 18 errors mixed together. The verification gate is what tells the difference.

### How this manifests in this codebase

- `cli/extractor.mjs` validates its own output (claimed-vs-parsed count check, skips HTTP 500s rather than emitting blank entries).
- `cli/validate.mjs` is itself the gate for generated PA-YAML — three-state (PASS/WARN/REFUSE) classification before `compile_canvas` is allowed to fire.
- `control-augmentations.yml` entries default to `verified: false`. Any entry that doesn't survive a `compile_canvas` round-trip is REMOVED, not left flagged false. Verification is binary: real or not.
- The pre-compile hook (`cli/precompile-hook.mjs` wired via `.claude/settings.json`) is the gate's runtime enforcement — every `compile_canvas` call in this project is intercepted and validated against the catalog first.
  - **Correction 2026-09-29:** no settings file in this repository currently registers the hook, so `compile_canvas` calls are **not** intercepted here. Found when a maintainer-authorized compile passed a strict BLOCK unchallenged. Until it is re-wired, the gate is procedural: run `validate_yaml` and get explicit authorization. Re-wiring needs an owner-approved override for apps with pre-existing refusals (acceptance record, 2026-09-29).
  - **Observed 2026-09-29:** `compile_canvas` can report "Validation FAILED" and still apply the source to the live session; a sync afterwards returned the compiled files byte-identically. A failed overall verdict is therefore not proof of rejection. Judge a claim by the per-property diagnostics for it, and confirm with a sync.

### Application to future work

Before adding any new structural component:

1. Identify what its outputs are.
2. Identify what makes those outputs *substance-wrong*, not just syntax-wrong.
3. Build the gate that catches the substance-wrong cases before downstream code relies on the outputs.
4. The gate is an artefact of the same magnitude as the component itself, not an afterthought.

**If a component has no gate, it's a liability, not an asset.**

## Durability honesty: what's actually the product

Two maintained layers in this codebase, with different lifespans:

- **The catalogs** (`catalogs/control-*.yml`) are *tooling output*. Anyone running `cli/extractor.mjs` against any tenant gets a tenant-specific version. They're reproducible artefacts, not durable IP. Re-extract after Power Apps monthly releases.
- **The verification gate** (`cli/validate.mjs` + the pipeline doctrine in `cli/PIPELINE.md` + the precompile hook) is a *pattern*, not a tool. The principle — three-state validator runs before any irreversible/expensive downstream step — is what's portable. Others can copy the pattern into their own pipelines without copying the code.

The gate is the protocol that makes the extracted catalogs trustworthy.

## Working in this codebase

### Catalog changes
- `control-manifest.yml` and `control-properties.yml` are auto-generated by `cli/extractor.mjs` — never hand-edit.
- `control-augmentations.yml` is the only catalog file safe to hand-edit. Entries default to shorthand (implicit `verified: false`). Verify by writing a minimal PA-YAML that uses the property and running it through `cli/validate.mjs` + `compile_canvas`. Promote to longhand `verified: true` on success; remove on rejection.
- Re-run the extractor after any Power Apps monthly release. The `extracted_at:` field is the staleness signal.

#### `dump_sourced_controls:` (schema_version 3+)
- The second hand-editable section of `control-augmentations.yml`. It holds controls the extractor **cannot** describe (`describe_control` HTTP 500) but that the user can insert in Studio, recovered from a Studio PA-YAML export (`catalogs/sources/studio-export-<date>.yaml`).
- **Studio emission counts as verification.** A control present in a Studio export, with the properties Studio emitted, is confirmed-real. Record `source: studio-export-<date>` (and `verified_by:` for augmentation entries like PowerBI.WorkspaceId).

### Evidence classes — what each `verified_by` value is worth

Three classes exist; a stamp must name the class the evidence actually belongs to. Overclaiming is how a wrong diagnosis shipped stamped `compile_canvas` on 2026-07-19 (see the v2.3.1 CHANGELOG entry).

| `verified_by` | What it proves | Promotion path |
|---|---|---|
| `compile_canvas` | Strongest. The claim survived a compile round-trip against a live tenant. Required for anything entering `additional_input_properties` as `verified: true`. | Terminal — this is the bar. |
| `studio-export-<date>` | A control/property exists because Studio itself emitted it. Property lists are **lower bounds** (Studio emits only non-defaults), so unknown props on these controls WARN rather than REFUSE. | Promote individual properties to `compile_canvas` when a round-trip exercises them. |
| `runtime_observation` | Weakest. A runtime behaviour observed in Studio or the player — a render symptom, a platform action's effect, a materialization artefact. Sufficient for troubleshooting entries and upstream bug reports; **never** sufficient to add a catalog property or flip an augmentation to `verified: true`. | Re-verify as `compile_canvas` if the finding ever becomes a catalog claim; otherwise it stays an observation and says so. |

**`runtime_observation` entries are structured claims, not anecdotes** (decided 2026-08-11). A new entry must record four things: **claim scope** (which of `compiler_accepts` / `roundtrip_preserves` / `studio_materializes` / `studio_renders` / `player_behaves` the observation is actually about), **environment** (Studio/server version or tenant where observed), **reproduction** (the minimal steps or YAML that produced it), and a **falsification test** (what observation would disprove it — if the falsifier is compile-checkable, the entry is a candidate for auto-enrollment in the verification queue). *Naming/alias:* this class was called `studio-observation` before 2026-08-11; ingestion accepts the old name as an alias for one release (through v2.5), after which it is an error. Historical stamps are not rewritten.

If you cannot name the class honestly, the finding goes in the verification queue instead of getting a stamp.

### Disproofs register

`disproofs.md` (this folder) is the permanent ledger of claims that were **tested and falsified** — starting with the founding 18 rejections. A disproven claim is the strongest knowledge the doctrine produces (it cost a live-tenant test to earn), and re-believing one is the most preventable failure. Rules:

- Every claim removed after failing verification gets a row in the register the same session — removal without registration re-arms the trap.
- Errata/ingestion work checks incoming claims against the register **before** anything else; a match means the burden of proof flips to the new evidence (a fresh, stronger-class verification), not to the register.
- **These property lists are LOWER BOUNDS** — Studio emits only non-default properties. So the validator treats an unknown property/variant on a dump-sourced control as **WARN** (`partial-catalog-data`), never REFUSE: refusing a plausible-but-unrecorded property on a real control is the cardinal gate failure. Known props/variants PASS; the WARNs feed the verification queue. This never leaks to extractor-reachable controls (they still REFUSE unknown props).
- **Retire on extraction.** The moment `cli/extractor.mjs` can reach a dump_sourced control, its entry is stale (a lower-bound list would mask the real one). The build gate (`server/scripts/build-catalog.mjs`) enforces this: a dump_sourced control that also exists in the manifest fails the build with `retire its dump_sourced entry`. An empty block is the healthy state when the extractor reaches every control. The lower-bound mechanism remains for the next extraction error; while the block is empty, injected-catalog unit tests cover its WARN paths instead of requiring an impossible production-corpus occurrence.
- Structural changes to this file are taught to **one** parser: `server/scripts/build-catalog.mjs` (→ generated `catalog.ts`); the analyzer core independently validates the injected result (`server/src/core/catalog.ts`). The old teach-both-parsers rule died with the v2.4.5 collapse.

### One semantic core, two execution surfaces (decided 2026-08-11, LANDED v2.4.5 / 2026-08-27)

The old invariant — "the worker validator and the local CLI validator are twins, maintained in parallel" — is **dead**. Two independent implementations of the same semantics is not redundancy, it is a skew generator (the collapse's oracle retroactively proved it: five component-family messages had silently diverged between the twins). The standing invariant:

- **One analyzer core** (`server/src/core/`, dependency-free, data injected) owns all validation/lint semantics.
- **Two execution surfaces** — the Worker adapter (`server/src/lib/` shims) and the CLI adapter (`cli/validate.mjs` over the committed single-file artifact `cli/dist/analyzer-core.mjs`) — are independently *tested*, but neither reimplements semantics. The artifact self-identifies (`ANALYZER_CORE_VERSION` in every output); vendored copies are one file.
- **Every rule release runs the acceptance corpus** (`npm run corpus`, external delivery roots via `APPFORGE_CORPUS_EXTERNAL_ROOTS`) with all discrepancies adjudicated before shipping.
- The one-release frozen validator was retired on 2026-08-28 in v2.4.6. `npm run corpus` is now a golden-snapshot gate: repository-owned inputs are path/hash pinned, delivery inputs are keyed by content hash, exact intended differences require committed spec-referenced adjudications, unused adjudications fail, and the expected-rules coverage tripwire remains mandatory.

### Generation rules
- `generator-rules.md` is the canonical contract for emitted YAML.
- `Control:` is rendered as the bare type — no `@version` suffix. The MCP doesn't expose per-control versions and the current PA-YAML schema dropped them.
- `cli/PIPELINE.md` documents the gate-before-compile order. Anything that emits PA-YAML must pass through `cli/validate.mjs` first.

### Don't
- **Don't bypass the gate.** If the gate refuses something legitimate, the catalog is wrong — fix the catalog, don't disable the gate.
- **Don't add unverified augmentations and ship them.** The 18-of-21 result is what happens when verification slips. If you're adding to `control-augmentations.yml`, verify in the same session.
- **Don't conflate "the MCP doesn't surface this" with "this exists."** The verification gate is the only mechanism that distinguishes them. Skepticism by default for any hand-augmentation claim, including ones you're confident about.
